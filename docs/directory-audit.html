问题清单

严重 apps/api/src/ — 40 个文件平铺无分组

这是最大的结构问题。所有源文件平铺在一个目录里，没有按功能分子目录。路由、OAuth、webhook 事件处理器、轮询器、工具、存储等不同关注点全部混在一起。

应该拆分为: src/ ├── routes/ (admin, knowledge, routine, content, agent, runtime, billing...) ├── webhooks/ (slack-events, telegram-events, whatsapp-events, twilio, vapi) ├── oauth/ (google-oauth, microsoft-oauth) ├── pollers/ (google-calendar-poller, google-routine-poller) ├── tools/ (harness-tools, workspace-tools) ├── lib/ (auth, code-runner, content-storage, voice)
严重 4 个巨型文件 (每个超 1000 行)

index.ts (1204行)、admin-routes.ts (1013行)、harness-tools.ts (1217行)、app.ts (1116行)。这些文件承担了过多职责，难以导航和维护。

apps/api/src 总计 11,137 行 其中 top 4 文件占 4,550 行 = 41% 的代码集中在 4 个文件里
严重 apps/web/ — 3 个巨型文件，无构建系统

前端是纯 vanilla JS：app.js (4257行)、index.html (1965行)、styles.css (3090行)。没有模块化、没有 src/ 目录、没有构建工具。ARCHITECTURE_GAPS.md 已承认这是已知差距（真实 Town.ai 用 Next.js 16）。

apps/web/package.json 的 dependencies 为空 {} 唯一脚本是 "check": "node ../../scripts/check-web.mjs"
中等 7 个包是单文件包 (index.ts only)

channels (677行)、content (609行)、operations (606行)、google (370行)、suggestions (333行)、billing (296行)、a2a (203行) 的全部逻辑塞在一个 index.ts 里。对比之下，knowledge 包有 15 个文件、runtime 有 10 个，结构合理。

中等 @town/db → @town/harness 分层倒置

packages/db/src/harness-thread-store.ts 导入了 @town/harness，导致低层的 db 包依赖了高层的 harness 包。虽然没有循环依赖，但违反了分层原则。harness-thread-store 应该移到 harness 包或 runtime 包里。

packages/db/package.json: "dependencies": { "@town/harness": "file:../harness", ... } packages/db/src/harness-thread-store.ts: import { ... } from "@town/harness";
轻微 两个 "api" 目录容易混淆

根目录的 api/（Vercel serverless 入口）和 apps/api/（实际 API 应用）同名。虽然这是 Vercel 的约定（根 api/ 是 functions 目录），但对新人来说容易困惑。可以考虑在 api/index.js 顶部注释中更明确地说明关系。

做得好的地方

优点 Monorepo 骨架规范

apps/ + packages/ 分离、每个包统一结构 (src/ + test/ + package.json + tsconfig)、pnpm workspace 配置正确、catalog 统一 zod 版本。

优点 包边界与依赖流清晰

17 个包按职责划分（contracts → db → identity/knowledge/agents/runtime → tools/harness），无循环依赖。文档 PACKAGES.md 明确记录了每个包的职责和依赖流。

优点 测试覆盖全面

apps/api 有 39 个测试文件，几乎每个路由都有对应测试。packages 层也有独立测试。顶层 test/ 做集成测试（Testcontainers PostgreSQL）。

优点 文档与自省

GOAL.md（目标+约束）、implementation-status.md（功能矩阵）、ARCHITECTURE_GAPS.md（已知差距）、PACKAGES.md（包参考）——项目对自身状态有清晰记录。

优点 构建验证脚本

6 个 check 脚本（source-only、runtime-config、build-entries、web）+ pnpm verify 一键全检。构建产物和敏感文件都被 gitignore。

总结

整体评价：骨架干净，血肉混乱。

Monorepo 的包划分、依赖流、测试策略、文档体系都是专业水准。包层（packages/）的结构基本合理——核心包（contracts, db, knowledge, runtime, harness）文件组织得当。

真正的混乱集中在两个地方：apps/api/src/ 是一个 40 文件平铺、4 个超千行巨型文件的"大杂烩"目录；apps/web/ 是 3 个无模块化的巨型文件。另外有 7 个包是单文件包，以及一个 db→harness 的分层倒置。

不乱的部分占大头（约 75%），但 apps/api 和 apps/web 这两个最常改动的应用层恰好是最乱的地方，所以日常开发体验会比较差。优先级建议：先拆 apps/api/src/ 的目录结构，再拆巨型文件，最后考虑 apps/web 的 Next.js 重写。
